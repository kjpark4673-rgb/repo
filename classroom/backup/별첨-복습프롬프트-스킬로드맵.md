Nov 12, 2026 · @james

## 이 문서 사용법

이 문서는 12월 말 수료까지 쓰는 복습·실습 별첨입니다. 오후 실습 시간마다 조별로 펼쳐 두고, 조장이 체크리스트로 진행을 확인합니다.

비유하면 등산 지도입니다. 1단계는 둘레길(스킬 하나 만들기), 2단계는 중턱(스킬 여러 개 연결하기), 3단계는 정상(내 회사용 에이전트 팀과 포트폴리오)입니다. 누구도 정상부터 오르지 않습니다.

### 배우는 순서

1. 강사가 그 주의 스킬을 먼저 만들어 보고 막히는 지점을 메모합니다.
2. 조장이 실습 전날 같은 스킬을 직접 돌려 봅니다. 강사 메모로 막힌 곳을 미리 풉니다.
3. 실습 시간에 조원이 따라 하고, 조장이 15장 체크리스트로 확인합니다.
4. 먼저 끝난 조원이 늦은 조원을 돕습니다. 조장은 혼자 다 가르치지 않습니다.
5. 조장이 못 푼 문제만 강사에게 올립니다.

### 누가 어디를 보나

| 누가 | 언제 | 먼저 볼 곳 |
| --- | --- | --- |
| 강사 | 매주 월요일 수업 전 | 스킬 로드맵, 오후 실습 운영 |
| 조장 | 실습 전날, 실습 중 | 그 주의 부서별 스킬, 조장 체크리스트 |
| 조원 | 실습 중, 복습할 때 | 복습 프롬프트 리스트, 내 희망 부서 장 |

### 표기 규칙

- 프롬프트의 `[대괄호]`는 내 브랜드·회사로 바꿔 넣는 자리입니다.
- `[실데이터 입력]`은 AI가 아니라 내가 공식 출처에서 채우는 칸입니다. 숫자와 후기는 지어내지 않습니다.
- 모든 스킬은 `.claude/skills/<스킬이름>/SKILL.md`에 저장합니다. 이 위치여야 Claude Code가 스킬로 인식합니다.

## 복습 프롬프트 리스트

복습할 때는 아래 20개를 순서대로 다시 돌리면 됩니다. P01\~P11은 지난 수업 주제를 복습용으로 다시 쓴 것이고, 원본 프롬프트는 각 날짜 공지 시트의 링크에 있습니다. P12\~P20은 오늘 쓴 프롬프트 그대로입니다.

### P01 · Day 1 · 학습 목표 문장

```
나는 [희망 직무] 취업을 준비하는 [전공/경력]이야. 과정이 끝났을 때 이룰 목표를 숫자·기한·결과물이 들어간 한 문장으로 3개 제안해줘. 그중 하나를 골라 주차별 중간 목표로 쪼개줘.
```

### P02 · Day 2 · 퍼소나와 고객여정 기초

```
[희망 기업]의 [대표 제품] 고객 퍼소나 3개를 만들어줘. 퍼소나마다 페인포인트 3개와 해결책 인사이트를 표로 정리하고, 가장 중요한 퍼소나 1명의 고객여정지도를 6단계로 그려줘. 모르는 수치는 [실데이터 입력]으로 남겨.
```

### P03 · Day 4 · 제안서 v1

```
[기업]에 제출할 [주제] 제안서 초안을 만들어줘. 구성은 문제 정의 / 타겟 고객 / 해결책 / 실행 계획 / 기대 효과. 모든 주장에 근거 칸을 두고, 근거가 없으면 [실데이터 입력]으로 표시해줘.
```

### P04 · Day 5 · 공격팀

```
너는 까다로운 팀장이야. 위 제안서의 약점을 근거 부족 / 논리 비약 / 실행 불가능 / 숫자 없음 4가지로 나눠 최소 20개 지적해줘. 심각한 순서로 정렬하고, 각각 고치는 방법을 한 줄로 붙여줘.
```

### P05 · Day 5 · 보강팀

```
공격팀 지적 중 상위 5개를 주장-근거-간증(실제 고객 후기) 구조로 보강해서 제안서 v2를 만들어줘. v1과 바뀐 곳을 표로 보여주고, 출처 없는 숫자는 [실데이터 입력]으로 남겨.
```

### P06 · Day 5 · 자료 아카이빙(냉장고 정리)

```
archive/ 폴더의 자료를 읽고 metadata.csv를 만들어줘. 열은 파일명, 출처 URL, 수집일, 자료 유형, 한 줄 요약, 태그. 출처가 없는 자료는 따로 표시해줘.
```

### P07 · Day 6 · USP와 블로그 플래닝

```
[제품]의 고객 후기를 바탕으로 고객이 흥미로워할 USP 소구점 10개를 뽑아줘. USP마다 근거가 된 후기 문장을 붙이고, 그중 3개로 블로그 글 5편의 제목과 목차를 플래닝해줘.
```

### P08 · Day 7, 9\~10 · 카드뉴스와 릴스

```
USP [번호]로 인스타 카드뉴스 5장(장마다 헤드라인 15자 이내 + 본문 2줄)과 15초 릴스 대본(0~3초 훅 / 3~12초 전개 / 12~15초 행동 유도)을 만들어줘. 브랜드 톤은 [톤 설명].
```

### P09 · Day 8 · 사업 기회와 워크플로우

```
[지역]의 [업종]에서 로컬 비즈니스 기회 3개를 찾아줘. 각각 고객, 문제, 수익 구조를 한 줄씩. 그중 하나를 실행할 때의 업무 흐름을 입력 → 처리 → 출력 → 검증 4칸으로 정리해줘.
```

### P10 · Day 11, 13 · BM과 가치사슬

```
[기업]의 비즈니스 모델 캔버스 9칸을 채워줘. 그리고 가치사슬(조달-생산-물류-마케팅·판매-서비스)에서 병목이 될 만한 구간 2곳과 그 이유를 알려줘.
```

### P11 · Day 12 · 퍼소나 스킬 저장

```
지금까지 퍼소나를 분석한 방식을 .claude/skills/persona/SKILL.md로 저장해줘. 맨 위에 name과 description을 적고, 입력 슬롯(브랜드·제품·타겟·상황), 분석 순서, 출력 형식, 지어내지 않기 규칙을 포함해줘.
```

### P12 · Day 14 · 퍼소나 + 고객여정 마스터 스킬

```
내 작업 폴더의 .claude/skills/persona-cjm/ 폴더에, 어떤 산업(뷰티 영상, 오프라인 팝업/전시, 여행·웰니스 상품 기획)에도 재사용할 수 있는 마스터 스킬 파일 SKILL.md를 만들어줘. 파일 맨 위에는 name과 description(언제 쓰는 스킬인지)을 적어줘.

[SKILL.md 필수 구조]
1. 입력 슬롯: BRAND / ITEM / TARGET / SITUATION
2. 타겟 퍼소나 딥다이브 (5-Whys 결핍 분석): 나이·직업 말고 '진짜 짜증 나는 일상 속 순간'을 5번의 Why로 파고들기. 마지막은 감정·바라는 자기 모습. "이 사람은 ___ 하고 싶은데 ___ 때문에 못 한다" 한 줄 요약.
3. 6단계 고객여정지도: [1 문제 자각] → [2 릴스/검색 탐색] → [3 경쟁사 비교 & 의심] → [4 구매 트리거] → [5 첫 사용] → [6 바이럴/재구매]. 단계별로 속마음 대사 / 이탈 이유 / 훅 카피를 표로.
4. 출력 스위치: 모드 A 15초 릴스 / 모드 B 오프라인 팝업 / 모드 C 여행 테마 투어. 모드를 부르면 해당 기획서를 HTML로 출력.
5. 규칙: 스펙·가격·수치·후기는 지어내지 말고 [실데이터 입력]으로 남길 것.

[오늘의 공통 사례]
BRAND: 라라스윗 / ITEM: 저당 아이스크림 파인트 / TARGET: 다이어트 중이지만 밤마다 디저트가 당기는 2534 여성 직장인 / SITUATION: 야근 후 밤 10시, 릴스를 보며 죄책감 없는 디저트를 찾는 순간

먼저 SKILL.md를 만들고, 위 사례로 퍼소나와 6단계 CJM 표를 도출해줘. 모든 결과는 한국어로.
```

### P13 · Day 14 · 5-Whys가 얕을 때

```
5-Whys가 같은 말을 반복하고 있어. 각 답이 행동 → 상황 → 제약 → 과거 경험 → 바라는 자기 모습 순서로 한 단계씩 깊어지게 다시 써줘.
```

### P14 · Day 14 · 퍼소나 장면이 안 보일 때

```
퍼소나의 짜증 모먼트를 시간, 장소, 손에 든 물건, 혼잣말이 보이는 한 장면으로 다시 써줘. 영상 첫 장면으로 바로 찍을 수 있을 정도로.
```

### P15 · Day 14 · 출처 없는 내용 자백시키기

```
방금 결과에서 출처 없이 쓴 숫자, 후기, 제품 정보를 전부 목록으로 뽑아줘. 각각 [실데이터 입력]으로 바꿔줘.
```

### P16 · Day 14 · 스킬 백업

```
SKILL.md를 SKILL_v1_오전.md로 복사해줘. 앞으로 SKILL.md는 내가 수정하라고 할 때만 고쳐.
```

### P17 · Day 14 · 모드 A 15초 릴스

```
SKILL.md는 수정하지 말고, 방금 분석한 퍼소나와 CJM(특히 1단계 짜증 모먼트와 3단계 의심 구간)을 근거로 [모드 A: 15초 인스타 릴스/쇼츠 영상 제작 기획안]을 HTML로 만들어줘. 첫 3초 비주얼 훅, 나레이션 대본, 컷별 화면 구성표(초/화면/자막/사운드), 생성형 AI용 이미지·영상 프롬프트까지. 근거 없이 쓴 문장은 마지막에 목록으로.
```

### P18 · Day 14 · 모드 B 성수 팝업

```
SKILL.md는 수정하지 말고, 퍼소나와 CJM을 근거로 [모드 B: 성수동 오프라인 팝업스토어 공간 동선 기획안]을 HTML로 만들어줘. 포토존(1단계) → 시식·체험존(3단계) → 구매·인증 이벤트(6단계) 동선, 존별 CJM 매핑, 스태프 응대 매뉴얼(의심 질문 Q&A, 냉동 보관·시식 운영 포함).
```


## 스킬 마스터 프롬프트 (15년 차 비법 전수형)

부서별 스킬은 모두 이 마스터 프롬프트 하나로 만듭니다. 공통 틀 아래에 각 부서 장의 “내공 주입 블록”을 붙이면, 신입이 그대로 따라 해도 대리급 결과가 나오는 긴 스킬 문서가 만들어집니다.

비유하면 지금까지의 프롬프트는 레시피 카드 한 장이었습니다. 마스터 프롬프트는 15년 차 셰프의 주방 매뉴얼입니다. 레시피에 더해 왜 그렇게 하는지, 신입이 자주 태우는 지점, 맛 검수 기준, 망쳤을 때 복구하는 법까지 들어 있습니다.

| 비교 | 기초 프롬프트 | 마스터 프롬프트 |
| --- | --- | --- |
| 시작 | 바로 결과물 생성 | 먼저 나를 인터뷰하고 설계안을 확인받음 |
| 분량 | SKILL.md 한 파일, 수십 줄 | SKILL.md + 비법·실수·예시·양식 파일 5개 |
| 내용 | 무엇을 할지 | 무엇을, 왜, 어떤 기준으로, 막히면 어떻게 |
| 품질 관리 | 없음 | 평가표, 셀프 검증 10개, 공격·보강 후 v2 |
| 사실 규칙 | 없음 | 실데이터만, 확신 없는 관행은 \[현업 확인 필요\] |

**사용 순서**

1. 아래 공통 마스터 프롬프트를 복사하고 \[대괄호\] 슬롯을 채웁니다.
2. 내 희망 부서 장의 “내공 주입 블록”을 바로 아래에 붙여 한 번에 보냅니다.
3. Claude가 인터뷰 질문을 하면 성실히 답합니다. 이 답이 스킬의 품질을 정합니다.
4. 설계안(폴더·목차)을 확인하고, 빠진 내용이 있으면 추가를 요청합니다.
5. 시험 운전 결과를 보고, 공격·보강을 거친 v2까지 받습니다.
6. v2를 현직자에게 보여 줄 수 있으면 한 줄 피드백을 받아 v3에 반영합니다(링크드인 커피챗 활용).

AI가 실제로 15년 경력을 가진 것은 아닙니다. 업계에 이미 정리된 방법론, 여러분이 모은 실데이터, 현직자 확인이 합쳐져야 진짜 내공이 됩니다. 그래서 프롬프트에 “확신 없는 관행은 표시하라”는 규칙을 넣었습니다.

### 스킬 폴더 구조

```
.claude/skills/<스킬이름>/
├─ SKILL.md                 ← 핵심 흐름과 규칙 (언제 어떤 파일을 읽을지도 여기에)
├─ references/
│   ├─ playbook.md          ← 현업 비법: 프레임워크, 지표 공식, 상황별 판단 기준
│   └─ pitfalls.md          ← 주니어 실수 사례집
├─ templates/
│   └─ output.md            ← 결과물 양식 (보고서·기획서)
└─ examples/
    └─ good-vs-bad.md       ← 같은 입력의 나쁜 결과와 좋은 결과
```

SKILL.md에는 핵심만 두고, 긴 설명과 사례는 폴더로 나눕니다. Claude가 필요할 때만 꺼내 읽어서, 문서가 길어져도 느려지지 않습니다.

```
# [내공 주입 블록 · 마케팅팀]

## A. 이 부서 스킬에 반드시 담을 현업 기준
1. 목표의 3단 연결: 사업 목표(매출·점유율) → 마케팅 목표(누가 어떤 행동을 얼마나) → 측정 지표(KPI).
   셋이 한 줄로 이어지지 않으면 결과물을 반려한다는 규칙을 넣어라.
2. 퍼널별 지표 사전(계산식 포함):
   인지 = 도달, 빈도, CPM(비용÷노출×1,000) / 고려 = CTR(클릭÷노출), 조회 완료율, 브랜드 검색량
   전환 = CVR(전환÷클릭), CPA(비용÷전환), ROAS(광고 매출÷광고비) / 유지 = 재구매율, LTV
   지표마다 “이 숫자가 말해 주지 못하는 것”도 적어라.
   (예: CTR은 높은데 전환이 낮으면 소재가 한 약속과 랜딩이 다르다는 신호)
3. 타겟 정의: 인구통계가 아니라 상황·결핍으로. 핵심 1개, 확장 1개, 일부러 버리는 타겟 1개를 이유와 함께.
   persona-cjm 스킬 결과 파일을 입력으로 받는다.
4. 메시지 구조: 핵심 메시지 한 문장(SMP), 그것을 믿게 하는 근거 3개(RTB),
   톤 가이드(쓰는 말 5개 / 쓰지 않는 말 5개).
5. 채널 역할: 페이드(유료)·온드(자사)·언드(입소문)를 구분하고, CJM 단계별로 어느 채널이 무슨 역할인지 표로.
   예산 배분은 숫자보다 “왜 이 비중인가”를 먼저 쓰고, 테스트용 예산을 따로 떼는 이유를 적는다.
6. 테스트 설계: 가설 문장은 “[변화]를 주면 [지표]가 오른다, 왜냐하면 [고객 인사이트]” 형식.
   한 번에 한 변수만 바꾼다. 결론 전에 기간과 표본이 충분한지 확인한다.
7. 성과 해석 순서: 숫자 변화 → 원인 후보 3개(타겟·소재·랜딩·외부 요인) → 확인 방법 → 다음 액션.
   원인을 하나로 단정하지 않는다.
8. 규제·리스크: 일반 식품은 질병 예방·치료 효과처럼 보이는 표현 금지(식품표시광고법),
   인플루언서 협업은 광고 표기 의무(공정위 추천·보증 심사지침), 비교 광고는 근거 자료 보관.
   표현이 애매하면 [법무 확인 필요]로 표시한다.
9. 팀장이 반드시 묻는 질문과 답하는 법: 왜 이 타겟인가 / 이 예산으로 무엇을 기대하나 /
   실패를 언제 어떻게 알아보나 / 경쟁사는 무엇을 하고 있나 / 지난번과 무엇이 다른가 (나머지 5개는 네가 채워라).
10. 주니어 실수: 채널부터 고르기, 지표 없이 “반응 좋았다”, 모든 고객에게 말하기,
    소재만 바꾸고 랜딩 방치, 한 번에 여러 변수 테스트, 초반 며칠 숫자로 결론 내기.
```

```
## A. 이 부서 스킬에 반드시 담을 현업 기준
1. 결정 질문부터: 조사는 “어떤 의사결정을 돕나”에서 시작한다.

3. 표본과 편향: 후기는 아주 만족하거나 아주 불만인 사람이 더 남기고, 사지 않은 사람의 목소리는 없다.

5. 인사이트 문장 형식: “[누가] [상황]에서 [행동·감정]한다. 왜냐하면 [이유]. 그래서 [기회].”

   차이가 크면 가정을 다시 본다. 모든 가정에 출처 또는 [가정] 표시.
8. 윤리: 이름·아이디·연락처는 지운다. 인터뷰는 녹음·활용 동의를 받는다.

9. 보고받는 사람이 반드시 묻는 질문: 몇 명을 조사했나 / 그 사람들이 우리 타겟을 대표하나 /

10. 주니어 실수: 결론을 정해 놓고 증거 모으기, 인용만 나열하고 해석 없음, 빈도만 세고 강도 무시,
```

개발·서비스기획팀 에이전트는 아이디어 한 줄을 기획 문서와 실제로 눌러 볼 수 있는 화면까지 바꿉니다. PM·서비스기획자·개발자·AI 에이전트 컨설턴트 지망생이 대상입니다.

| 단계 | 스킬 | 하는 일 | 실습 예제 | 작업물 | 얻는 이득 |

```
# [내공 주입 블록 · 개발·서비스기획팀]

## A. 이 부서 스킬에 반드시 담을 현업 기준
1. 문제 우선: 기능이 아니라 사용자 문제와 성공 지표에서 시작한다.
   “이 기능이 없으면 사용자는 지금 무엇으로 해결하나(대안)”를 반드시 적는다.
2. 범위 관리: MVP는 핵심 가설 하나를 검증하는 최소 범위다.
   Must / Should / Could / Won't(MoSCoW)로 우선순위를 나누고 “이번에 하지 않는 것”을 명시한다.
3. 요구사항 문장: 사용자 스토리 “[사용자]로서 [목적]을 위해 [기능]을 원한다” +
   인수 조건(Given-When-Then). “빠르게·쉽게” 같은 모호어는 측정 가능한 문장으로 바꾼다.
4. 예외 상황: 빈 상태, 오류, 로딩, 권한 없음, 네트워크 끊김, 입력 오류, 중복 제출.
   화면마다 정상 / 빈 화면 / 오류 3가지 상태를 설계한다.
5. 지표: 북극성 지표 1개 + 보조 지표(활성·전환·유지) + 가드레일 지표(나빠지면 안 되는 것).
   측정할 이벤트의 이름과 발생 시점을 정의한다(트래킹 계획).
6. 프로토타입 원칙: 클릭 가능한 최소 흐름, 실제 문구 사용(임시 문구 금지), 모바일 우선,
   접근성(글자 대비·크기·키보드 조작).
7. QA: 테스트 케이스 열은 ID / 전제 / 단계 / 기대 결과 / 실제 결과 / 상태.
   버그 리포트는 재현 단계·기대·실제·환경·심각도.
8. 데이터·보안: 개인정보는 최소만 수집한다. API 키를 코드나 문서에 적지 않는다.
   고객 데이터를 외부 AI에 넣기 전에 회사 정책을 확인한다 [현업 확인 필요].
9. 개발자·이해관계자가 반드시 묻는 질문: 왜 지금 이걸 하나 / 성공을 무엇으로 아나 /
   안 하면 무슨 일이 생기나 / 가장 위험한 가정은 / 일정에 맞나 (나머지 5개는 네가 채워라).
10. 주니어 실수: 해결책부터 정하기, 화면만 그리고 예외 없음, 지표 없는 PRD, 범위가 계속 커짐,
    개발자와 용어 불일치, 사용자 검증 없이 출시.
11. AI 에이전트 컨설턴트용: 현업 인터뷰 → 업무 흐름 4칸(입력·처리·출력·검증) →
    자동화 적합도 평가(반복성, 규칙성, 데이터 접근성, 틀렸을 때의 비용) → 스킬 설계 순서를 넣어라.

## B. 스킬별 추가 요구
- prd-writer: 1~2장. 문제 · 현재 대안 · 핵심 가설 · 지표 · 범위(하는 것/안 하는 것) · 리스크 · 열린 질문.
- user-story: 스토리 + 인수 조건 + 화면 목록 + 화면별 3가지 상태.
- prototype: 파일 하나짜리 HTML, 화면 전환, 실제 문구, 모바일 화면, 접근성 점검 목록.
- qa-cases: 정상·예외·경계값 케이스, 심각도 기준(치명·높음·보통·낮음)의 정의.
- structured-output: JSON 스키마(필드·타입·필수 여부·예시), 검증 규칙, 스키마 버전 표기.
- service-team: PRD→스토리→프로토타입→QA→릴리스 노트 순서, 파일 전달, 릴리스 노트 양식.
```

```
# [내공 주입 블록 · 운영·HR팀]

## A. 이 부서 스킬에 반드시 담을 현업 기준
1. SOP 원칙: 한 단계 = 한 동작, 동사로 시작. 단계마다 담당자·완료 기준·예상 소요 시간.
   “누가 해도 같은 결과가 나오는가”를 기준으로 쓴다.
2. 예외 처리: 정상 흐름 + 예외 흐름(문제가 생기면 누구에게 언제 보고) + 상위 보고 기준

3. 역할 정리(RACI): 업무마다 실행(R)·최종 책임(A)·협의(C)·통보(I)를 적는다.
4. CS 응대: 문의 유형 분류(배송·품질·환불·사용법·불만) → 1차 답변 템플릿 → 보상 권한표 → 상위 보고.
   답변은 사과 → 공감 → 해결 → 재발 방지 순서. 식품 이물·건강 이상 문의는 즉시 상위 보고하고 기록을 보존한다.
5. 주간 보고 형식: 3줄 요약 → 지표(목표 대비) → 완료·진행·지연(지연은 원인과 대책) →
   이슈와 도움 요청 → 다음 주 계획. 상태는 색깔 대신 “정상 / 주의 / 지연” 글자로도 쓴다.
6. 회의록: 결정사항 / 할 일(담당·기한) / 보류 / 다음 회의. 결정과 의견을 구분해 적는다.
7. 운영 지표: 처리 시간(리드타임), 처리 건수, 오류율, 첫 응답 시간, 재문의율, 고객 만족도.
   지표마다 정의와 계산 방법을 적는다.
8. HR: 채용 공고(JD)는 미션·주요 업무·필수/우대 요건·기대 성과.
   구조화 면접은 역량별 행동 질문(STAR: 상황·과제·행동·결과) + 평가 척도.
   직무와 무관한 개인정보(출신 지역·혼인 여부·재산·가족 등)를 묻지 않는다(채용절차법) [현업 확인 필요].
9. 보고받는 사람이 반드시 묻는 질문: 지금 막힌 게 무엇인가 / 언제 끝나나 / 리스크는 /
   내가 무엇을 도와야 하나 / 지난주에 한 약속은 지켰나 (나머지 5개는 네가 채워라).
10. 주니어 실수: 경험에만 기대는 업무 설명, 예외 흐름 없음, 결론 없는 보고,
    받아쓰기식 회의록, 문제를 늦게 공유, CS에서 권한 밖의 약속.

## B. 스킬별 추가 요구
```

## ⑥ 재무·경영전략팀

재무·경영전략팀 에이전트는 기획안에 “그래서 얼마가 남는가”를 붙입니다. 내일(Day 15) 배우는 매출 공식이 출발점이고, 재무분석·경영기획·사업분석·영업관리 지망생이 대상입니다.

```
   [현업 확인 필요]. 할인율 표시는 실제 판매 가격 기준이어야 한다.
9. 바이어·팀장이 반드시 묻는 질문: 왜 우리 채널인가 / 경쟁 상품 대비 무엇이 낫나 /

10. 주니어 실수: 내 취향으로 상품 판단, 할인으로만 매출 만들기, 마진 계산 누락,
```

```
# [내공 주입 블록 · 데이터분석·AI 리서치팀]

## A. 이 부서 스킬에 반드시 담을 현업 기준
1. 분석 순서: 질문 → 지표 → 데이터 → 분석 → 결론 → 액션.
   시작 전에 “이 분석으로 무엇을 결정하나”와 “결과가 A면 무엇을, B면 무엇을 한다”를 미리 적는다.
2. 데이터 점검: 행 수·기간·열 정의, 결측·중복·이상치, 단위·통화·시간대를 확인하고

3. 지표 정의서: 지표명 / 정의 / 계산식 / 데이터 출처 / 갱신 주기 / 담당 / 주의점.

5. 통계 기본: 평균만 보지 말고 분포·중앙값을 본다. 상관은 인과가 아니다. 표본 크기와 신뢰구간을 적는다.
   여러 번 비교하면 우연히 차이가 나오기 쉽다. 전체와 그룹별 결론이 뒤집힐 수 있다(심슨의 역설).
   A/B 실험은 시작 전에 표본 크기·기간·주 지표를 정하고, 중간에 결과를 보고 멈추지 않는다.
6. 재현성: 분석 단계를 코드나 노트로 남기고 원본 데이터는 고치지 않는다. 같은 입력이면 같은 결과.
7. LLM 출력 평가: 평가 기준(정확성·근거성·완결성·형식 준수·일관성)과 각 점수(1~5)의 뜻을 정의한다.
   같은 입력을 여러 번 돌리고, 사람 채점과 AI 채점을 비교한다.
   AI 채점은 긴 답에 점수를 더 주거나 제시 순서에 따라 달라질 수 있다는 점을 적는다.
8. 논문 읽기: 초록 → 그림·표 → 결론 → 방법 순서로 읽는다.
   문제 정의, 기존 방법 대비 차이, 데이터셋·평가 지표, 결과가 성립하는 조건, 한계를 정리한다.
   재현 계획에는 필요한 데이터·연산 자원·코드 공개 여부를 적고, 제목·저자·연도·링크를 인용한다.
9. 보고받는 사람이 반드시 묻는 질문: 이 데이터는 믿을 만한가 / 그래서 무엇을 하라는 건가 /
   우연일 가능성은 / 다른 설명은 없나 / 매주 자동으로 볼 수 있나 (나머지 5개는 네가 채워라).
10. 주니어 실수: 데이터 점검 생략, 결론 없는 차트 나열, 상관을 인과로 해석,
    작은 표본으로 일반화, 지표 정의 불일치, 가정값을 실제처럼 표시.

## B. 스킬별 추가 요구
- data-quality: 점검표(항목 / 결과 / 조치 제안) + 요약 통계 + “이 데이터로 답할 수 없는 질문” 목록.
- funnel-chart: 단계별 인원과 다음 단계로 넘어간 비율, 가장 크게 빠지는 구간 강조, 모든 값에 “가정” 표시.
- kpi-dashboard: 지표 정의서 먼저 → 요약 숫자 → 추이 → 세부 순서, 목표 대비 상태를 글자로도 표시.
- ab-test-readout: 실험 설계 요약 → 결과 → 유의성 → 결론 → 한계 → 다음 실험.
- llm-eval: 평가 기준표, 실행별 점수, 점수 차이의 원인, 프롬프트·스킬 개선 제안.
- paper-brief: 1장 요약 + 재현 계획 + “우리 업무에 쓸 수 있는 점” 3개.

## C. 시험 운전 입력
가상 커머스 주문 데이터(직접 생성, “가상” 표기) / 오늘 Step 1 결과 3개 / 관심 논문 PDF 1편
```

## ⑨ 영업·CRM팀

영업·CRM팀 에이전트는 “고객사 조사 → 첫 연락 → 제안 → 후속 관리 → 실적 보고”를 고객사마다 같은 품질로 돌립니다. 기술영업·B2B 영업관리·CRM 지망생이 대상입니다.

| 단계 | 스킬 | 하는 일 | 실습 예제 | 작업물 | 얻는 이득 |
| --- | --- | --- | --- | --- | --- |
| 1 | account-research | 고객사 → 사업·최근 이슈·조직·제안 포인트(공개 자료, 출처 표기) | 희망 B2B 고객사 1곳 | 고객사 분석 1장 | 첫 미팅 전 준비를 혼자 끝냄 |
| 1 | outreach-email | 고객사별 첫 메일 3종 + 후속 메일 2종 | 위 고객사 담당자(가상 인물) | 메일 시퀀스 | 답장을 부르는 메일 구조 |
| 2 | b2b-proposal | 고객 문제 → 제안서(현황·해결책·도입 효과·가격 옵션·일정) | 가상 고객사에 AI 에이전트 도입 제안 | B2B 제안서 | 기술영업·제안 직무의 핵심 산출물 |
| 2 | lead-nurture | 리드 단계별 메시지·콘텐츠 시퀀스 | 웨비나 신청자 리드(가정) | 리드 관리 캘린더 | CRM·마케팅 자동화 감각 |
| 3 | pipeline-report | 영업 기회 목록 → 단계별 금액·전환·다음 액션 | 가상 영업 기회 20건 | 월간 영업 보고서 | 영업관리 직무의 숫자 감각 |
| 3 | sales-team | 조사→메일→미팅 준비→제안→후속→보고 묶음 | 고객사 3곳 동시 진행 | 고객사별 제안서 + 영업 보고서 | 영업 전 과정을 보여 주는 포트폴리오 |

**보고서로 바꾸면:** 고객사 분석서(1단계), B2B 제안서·리드 관리 계획(2단계), 월간 영업 보고서(3단계)가 됩니다.

**회사에서 쓰는 법**

- 기술영업(IT·제조): 고객사가 바뀌어도 같은 구조의 맞춤 제안서를 빠르게 만듭니다.
- B2B SaaS: 리드 단계별 메시지와 파이프라인 보고를 스킬로 돌립니다.
- 영업관리: 지점·담당자별 실적과 예측을 같은 양식으로 보고합니다.

**내공 주입 블록 · 영업·CRM팀** (공통 마스터 프롬프트 맨 아래에 붙이기. 표의 6개 스킬에 모두 씁니다)

```
# [내공 주입 블록 · 영업·CRM팀]

## A. 이 부서 스킬에 반드시 담을 현업 기준
1. 고객사 이해: 고객사의 사업 목표·최근 이슈를 공시·보도자료·채용공고에서 읽고 우리 제안과 연결한다.
   의사결정 구조(실제 사용자·결정권자·예산 승인·구매 담당·영향력 있는 사람)를 표로 정리한다.
2. 질문 기반 영업: 미팅 전에 가설 질문 10개를 준비한다.
   상황 → 문제 → 문제가 낳는 영향 → 해결의 필요 순서(SPIN). 고객이 문제의 비용을 스스로 말하게 한다.
3. 리드 자격 판단: 예산·권한·필요·시기(BANT)로 우선순위를 정한다. 자격이 부족한 리드는 관리(너처링)로 넘긴다.
4. 메일 원칙: 제목은 고객 상황을 말하고, 첫 문장은 고객 이야기로 시작한다. 요청은 하나(예: 15분 통화), 짧게.
   후속 메일은 새로운 가치(자료·사례)를 들고 간다. 광고성 메일 규칙을 지킨다 [현업 확인 필요].
5. 제안서 구조: 고객 현황(고객의 언어로) → 문제와 그 비용 → 해결책 → 도입 효과(측정 가능, 가정 표기) →
   사례 → 일정·역할 → 가격 옵션 3안 → 다음 단계.
6. 도입 효과 계산: 줄어드는 시간 × 인건비, 늘어나는 매출, 도입 비용, 투자 회수 기간. 모든 가정을 표시한다.
7. 파이프라인 관리: 단계 정의(리드 → 자격 확인 → 미팅 → 제안 → 협상 → 계약), 단계별 전환율,
   가중 파이프라인(금액 × 단계 확률), 오래 멈춘 기회 표시(마지막 연락 후 경과일).
8. CRM 기록: 미팅마다 날짜·참석자·고객 발언 원문·다음 액션·기한을 남긴다.
9. 팀장이 반드시 묻는 질문: 이 고객은 왜 지금 사야 하나 / 결정권자는 누구인가 / 경쟁 제안은 /
   이번 분기 확정 가능 금액은 / 왜 이 가격인가 (나머지 5개는 네가 채워라).
10. 주니어 실수: 제품 설명부터 시작, 고객 조사 없는 복사 메일, 결정권자 모름,
    다음 액션 없는 미팅, 낙관적인 파이프라인, 후속 연락 누락.

## B. 스킬별 추가 요구
- account-research: 고객사 개요 / 최근 이슈 3개(출처 링크) / 예상 문제 / 제안 포인트 / 미팅 질문 10개.
- outreach-email: 메일마다 겨냥한 고객 상황과 요청 한 가지를 표시, 후속 간격은 가설로.
- b2b-proposal: 위 구조 + 도입 효과 계산 시트 + 예상 반론과 답변.
- lead-nurture: 단계 × 시점 × 메시지 × 콘텐츠 표, 다음 단계로 넘어가는 신호 정의.
- pipeline-report: 단계별 금액·건수·전환율, 가중 금액, 멈춘 기회 목록, 다음 달 예측과 근거.
- sales-team: 조사→메일→미팅 준비→제안→후속→보고 순서와 파일 전달, 고객사별 폴더 규칙.

## C. 시험 운전 입력
가상 고객사 “대전 소재 중견 식품 제조사”에 AI 에이전트 업무 자동화 제안 / 가상 영업 기회 20건(직접 생성)
```

## 스킬 결과물을 보고서·기획서로 바꾸는 법

스킬이 낸 결과물은 초안입니다. “결론 먼저 → 근거 → 다음 행동” 구조로 바꾸고 검증을 거쳐야 회사에 낼 수 있는 문서가 됩니다. 기획서는 앞으로 할 일을 설득하고, 보고서는 한 일과 결과를 공유합니다.

### 공통 양식

```markdown
# [제목: 결론을 담은 한 문장]
## 요약 (3줄): 무엇을 / 왜 / 무엇을 결정해 달라는지
## 배경과 목표
## 핵심 발견 (근거와 출처)
## 제안 (무엇을, 누가, 언제, 비용)
## 기대 효과와 측정 방법 (가정 표기)
## 리스크와 대응
## 다음 단계 / 결정 요청
## 부록: 데이터, 출처, 가정 목록
```

### 변환 프롬프트

```
방금 [스킬 이름] 결과를 [받는 사람: 팀장/임원/클라이언트]에게 제출할 [보고서/기획서]로 바꿔줘.
양식은 제목(결론 한 문장) / 3줄 요약 / 배경과 목표 / 핵심 발견 / 제안 / 기대 효과 / 리스크 / 다음 단계 / 부록.
다 만든 뒤 받는 사람 입장에서 약점 10개를 찾아 보강하고,
출처 없는 문장과 가정값을 마지막에 목록으로 보여줘. 요약만 읽어도 결정할 수 있게 써줘.
```

### 제출 전 체크포인트

| 체크포인트 | 확인 질문 |
| --- | --- |
| 결론 | 첫 문장만 읽어도 무엇을 하자는지 알 수 있나 |
| 숫자 | 모든 숫자에 단위·기간·출처가 있나 |
| 가정 | 가정값이 “가정”으로 표시돼 있나 |
| 질문 대비 | 내공 블록의 “팀장이 묻는 질문 10개”에 답이 들어 있나 |
| 다음 행동 | 할 일마다 담당과 기한이 있나 |
| 분량 | 요약 1장, 나머지는 부록으로 나눴나 |
| 표기 | 실존 브랜드 사례라면 “학습용 가상 기획안” 문구가 있나 |

## 링크드인 자기 PR과 취업 포트폴리오

채용 담당자는 “무엇을 할 줄 아나”보다 “무엇을 만들어 봤고 어떻게 생각하나”를 봅니다. 내가 만든 스킬과 결과물을 포트폴리오 하나로 묶고, 만드는 과정을 매주 링크드인에 올립니다. 자격증 한 줄보다 타깃 기업을 깊게 파고든 결과물이 훨씬 강합니다.

### 포트폴리오 구성

| 구성 요소 | 내용 | 예시 |
| --- | --- | --- |
| 한 줄 소개 | 직무 + 내가 자동화하는 업무 | “AI 에이전트로 리뷰 분석과 CRM 메시지를 설계하는 마케터 지망생” |
| 대표 프로젝트 3개 | 문제 → 만든 스킬 → 결과물 → 배운 점 | 라라스윗 퍼소나·CJM, 부서 스킬, 에이전트 팀 |
| 스킬 저장소 | GitHub에 .claude/skills 공개 + README | 개인정보·회사 자료는 지우고 올림 |
| 결과물 데모 | Netlify 등 웹 주소 | 기획서 HTML, 대시보드, 프로토타입 |
| 개선 기록 | v1 → v2 → v3 비교와 바꾼 이유 | 공격·보강 표 |
| 검증 | 현직자 피드백 한 줄(허락을 받은 경우만) | 커피챗 후 반영한 점 |

### 프로젝트 카드 양식

```markdown
## [프로젝트 이름]
- 문제: [어떤 회사의 어떤 업무가 왜 어려운가]
- 내가 만든 것: [스킬 이름]과 구조(입력 → 처리 → 출력 → 검증)
- 결과물: [링크] (스크린샷 1장)
- 개선 과정: v1의 약점 → v2에서 바꾼 규칙
- 배운 점: [한 문장]
- 입사하면: [이 스킬로 첫 달에 할 일]
```

### 링크드인 프로필 세팅

- 헤드라인: “\[직무\] 지망 | AI 에이전트로 \[업무\] 자동화 | \[대표 결과물 키워드\]”
- 소개: 3문단. 관심 있는 문제, 만든 것(링크 포함), 가고 싶은 회사에서 하고 싶은 일.
- 추천(Featured): 포트폴리오 주소와 대표 결과물 3개.
- 프로젝트·교육: 과정명, 기간, 만든 것.
- 기술: Claude Code, 프롬프트·스킬 설계, 퍼소나·고객여정 분석, 희망 직무 기술.

### 게시물 만들기 프롬프트

```
이번 주에 내가 만든 [스킬/결과물] 내용을 바탕으로 링크드인 게시물을 써줘.
구조: 첫 줄 훅(내가 푼 문제) → 문제 상황 → 내가 한 것(스킬 구조, 프롬프트 일부) →
결과(숫자는 실제인 것만, 가정은 가정이라고) → 배운 점 → 읽는 사람에게 던지는 질문 1개.
분량은 모바일 화면 두 번 스크롤 이내, 해시태그 3~5개. 내 말투로, 과장 없이.
```

### 주의할 것

- 회사 기밀·개인정보·후기 작성자 아이디는 올리지 않습니다.
- 실존 브랜드 사례는 “학습용 가상 기획안이며 브랜드와 무관”을 밝힙니다.
- 가정값을 실제 성과처럼 쓰지 않습니다. 면접에서 바로 들통납니다.
- 현직자 커피챗은 구체적인 질문 1개와 내 결과물 링크로 짧게 요청합니다.

### 지원할 회사에서 쓰는 법

- 자기소개서: “입사하면 첫 달에 \[스킬\]로 \[업무\]를 이렇게 하겠다”를 쓰고 결과물 링크를 붙입니다.
- 면접: 결과물을 3분 안에 화면으로 보여 주고, v1에서 v2로 무엇을 왜 바꿨는지 설명합니다.
- 과제 전형: 스킬로 초안을 빨리 만들고, 남는 시간을 검증과 인사이트에 씁니다.

## 오후 실습 운영: 조장 체크리스트와 상호보완

오후 실습은 조장이 정해진 시각마다 진행표를 확인하고, 막힌 조원은 조 안에서 먼저 해결합니다. 강사는 조장이 풀지 못한 문제만 받습니다.

### 역할

| 역할 | 하는 일 | 하지 않는 일 |
| --- | --- | --- |
| 강사 | 전날 시연·막힘 메모 공유, 조장 질문 답변, 빨간 카드 대응 | 조원 한 명을 처음부터 붙잡기 |
| 조장 | 전날 1회 실행, 시각별 진행 확인, 막힌 조원 연결, 17:40 보고 | 조원 대신 만들어 주기 |
| 조원 | 마스터 프롬프트 실행, 인터뷰 성실 답변, 짝꿍 결과물 리뷰 | 15분 넘게 혼자 붙잡기 |

### 막혔을 때 순서

1. 복습 프롬프트(P13\~P15)와 학생용 가이드의 “막히면” 구간으로 스스로 해결합니다.
2. 짝꿍에게 묻습니다.
3. 조장에게 묻습니다.
4. 조장이 못 풀면 강사에게 올립니다(빨간 카드).

15분 규칙: 한 단계에서 15분 넘게 막히면 강사 시연 결과물을 받아 다음 단계로 넘어갑니다. 원인은 16시 이후 클리닉에서 봅니다.

### 강사·조장 선행 학습 (실습 전날 30분)

1. 강사가 그 주 스킬을 먼저 돌려 결과물과 막힌 지점을 공유 폴더에 올립니다.
2. 조장은 같은 마스터 프롬프트를 자기 희망 부서로 한 번 돌려 봅니다.
3. 조장끼리 막힌 점을 시트 하나에 모으고, 강사가 답을 달아 둡니다.
4. 다음 날 조장은 그 답을 들고 조원 화면을 봅니다.

### 조장이 조원에게 전수하는 법

보여 주기 → 같이 하기 → 혼자 하기 → 설명하게 하기 순서입니다. 조원이 다른 조원에게 설명할 수 있으면 그 단계는 완료입니다. 마케팅 지망과 테크 지망을 짝지어 서로의 결과물을 리뷰하게 하면, 한쪽은 고객 관점을, 다른 쪽은 구조·검증 관점을 채워 줍니다.
