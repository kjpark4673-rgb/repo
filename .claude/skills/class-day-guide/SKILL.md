# 수업 날짜 하나를 가이드로 만드는 법

Day 16 가이드(6판, 11/14~15)를 만든 과정을 그대로 옮긴 작업 순서다. 비유하면 **매일 새 공연을 올리는 연출 노트**다. 대본(프롬프트)은 날마다 바뀌어도 대본 읽기 → 리허설(가상 학생 시험) → 관객 눈으로 보기(수강생 눈 검토) → 공연(발행) → 무대 감독 노트(강사 문서) 순서는 같다. 이 순서를 건너뛰었던 Day 15는 프롬프트 8개 중 6개가 수업 중에 멈췄다.

## 먼저 지킬 것 (어기면 수업이나 사람에게 실제 피해가 난다)

1. **강사가 명령한 날짜만 만든다.** "다음 날도 미리"는 하지 않는다. 강사가 앞서 "Day 17 자료는 내 명령 전에 절대 만들지 마"라고 했다. 명령이 없으면 계획만 말하고 멈춘다.
2. **학생 자료는 읽어서 배우되, 공개 저장소에는 아무도 식별되지 않게.** 강사가 공유한 학생 실습시트·회고·면담 내용은 적극적으로 읽고 개개인의 관심사와 고민을 파악한다(11/15 강사 지시). 다만 **저장소는 공개이고, 산출물에는 학생 실명, 학생별 메모, 드라이브 문서 식별자, 특정 개인의 고민이 그대로 드러나면 안 된다.** 반의 상태는 유형과 묶음 숫자로만 남긴다. 계약·메일 내용, 직원 이름, 강사 이메일도 넣지 않는다. 공유 설정은 Claude가 바꿀 수 없으니 강사에게 맡긴다. 로그인이 필요한 시스템(LMS)은 인증을 우회하지 않는다. 강사가 내보낸 파일을 읽는다.
3. **지어내지 않는다.** 강사의 이야기는 강사가 그 구간을 위해 한 말만 쓴다. 다른 구간에 옮겨 붙이거나 이야기와 수업을 잇는 결론을 만들지 않는다. 숫자·후기는 출처가 없으면 [채울 곳], 추측은 (가정)으로 둔다. 자료에는 출처를 나눠 적는다: 공식 일정표 / 강사가 한 말 / Claude의 해석.
4. **돌려 본 프롬프트만 발행한다.** 문구를 한 글자라도 바꾸면 다시 돌린다. 발행본의 상자가 모두 시험본과 글자 단위로 같은지 확인한다.
5. **묻지 말고 정한다.** 강사에게는 강사만 아는 것(교실에서 실제로 할 것, 현업 판단, 보기 고르기)만 한 번에 서너 개, 기본값을 붙여 묻는다. 나머지는 정하고, 정한 것을 알린다. "너무 깊게 들어가지 마"가 강사의 기준이다.
6. **강사에게 말할 때:** 새 개념은 비유로 설명하고, 업무 이야기에는 업무 워크플로우(입력 → 처리 → 출력 → 검증)를 붙인다. 학생 자료는 해요체로 쓴다.

## 입력 세 가지

| 입력 | 어디서 | 무엇을 뽑나 |
|---|---|---|
| 그날의 공식 줄 | 공식 일정표("상세 커리큘럼_최종" 탭, 강사 드라이브)와 `classroom/tools/build_glossary.py`의 DAYS | 학습 내용, 도구, 결과물, 트랙별 실습. 전날·다음 날 줄도 같이 본다 |
| 반의 상태 | 학생 실습시트, 공지 시트, LMS 내보내기, 만족도 설문 (읽는 법: `references/student-status.md`) | 기록이 멈춘 정도, 자기 회사로 하는 비율, 희망 직무 분포, 빠른 학생 수, 링크를 못 만드는 학생 수 같은 묶음 숫자 |
| 강사의 지시와 이야기 | `HANDOFF.md` 0번(규칙)과 가장 최신 7-xx, 이번 대화, 전날 강사 세션 기록 | 그날 꼭 할 것, 수업 예시, 쓸 수 있는 현업 이야기, 바꾸지 말 것 |

반의 상태는 자료를 "누구에게 맞출지" 정하는 데 쓴다. 학생 한 사람을 평가하거나 등급으로 나누는 데 쓰지 않는다. 상태 → 설계로 옮기는 예는 `references/student-status.md`에 있다.

## 작업 순서

각 단계는 산출물이 있어야 다음으로 간다. 수업 이틀 전 초안, 전날 밤 동결이 목표다(동결 뒤에는 오탈자만).

### 1. 공식 줄 대조표
그날의 공식 학습 내용·도구·결과물을 왼쪽에, 만들 구간을 오른쪽에 놓은 표를 대화에 먼저 보인다. 공식에 없는 것은 "강사 추가"로 표시하고 본선 뒤에 둔다. 전날 가이드와 겹치는 구간은 다시 넣지 않는다.

### 2. 강사와 짧은 문답
AskUserQuestion으로 한 번에 서너 개. 보기를 주고 기본값을 첫째에 둔다. Day 16에서 물은 것: 학생에게 줄 보기 목록, 오전 MVP의 모양, 자료를 어디서 구할지, 오후 메뉴, 수업 예시. 답은 강사의 말 그대로 기록한다.

### 3. 하루 설계
- **오전은 다 같이 하는 기초, 오후는 각자 고르는 심화.** 오전의 꼭 하는 프롬프트는 5~7개를 한 줄로 잇는다(Day 16: 규칙 → 채용 공고 → 설계서 → 첫 조사 → 보는 화면 → 다듬기). 오후는 메뉴 카드 4~5개에서 하나 이상, 카드마다 "끝나면 보이는 것"과 걸리는 시간을 적는다. 마무리는 포트폴리오 한 장(W2)이다.
- **방법은 같고 결과는 학생마다 다르게.** 같은 프롬프트에 학생이 적는 입력 칸(하고 싶은 일, 회사·제품·고객, 고른 보기)이 들어가 결과가 갈리게 한다. 보기 카드를 주고(Day 16은 일곱 장, 테크 트랙 카드 포함), 보기에 없는 것을 직접 적어도 되게 한다. 칸을 비우면 직무별 기본값으로 간다.
- **"내 결정" 네 곳**을 둔다. 초안은 Claude가, 결정은 학생이 한다. 결정은 대화에 한 줄로 말하게 해야 저녁 포트폴리오에 남는다.
- **수업 예시는 하나.** 강사가 정한다(Day 16: 라라스윗의 경쟁사 가격·프로모션 조사. 11/22 강사 문답부터 대표 업무는 "경쟁사·업계 동향 리서치"(주간 동향 리포트), 가격 비교는 대표 예시로 쓰지 않는다). 강사가 시연한다.
- 현업 문제를 실습 재료로 쓴다. 신입이 매일 손으로 하던 일을 AI 에이전트로 줄이는 것이 강사가 원하는 방향이다(Day 16: 광고 소재·가격·증정품·상세페이지 조사).

- **폴더 말은 하나로, 화면은 리모컨으로(11/21 강사 지시 "폴더 저장, 폴더 불러오기 이렇게 헷갈리는 거 적게").** 학생 화면에서 폴더는 "작업 폴더" 한 이름만 쓴다(지난주에 쓰던 폴더·같은 폴더·내 폴더·이 폴더로 바꿔 부르지 않는다). 준비 맨 위에 "작업 폴더는 하나만" 카드(열 때 · 저장 · 보기, 비유는 내 책상 서랍 하나)를 두고, 만든 화면은 리모컨 맨 위 "화면 열기" 상자로 띄운다(폴더 열고 더블클릭하던 두 단계를 하나로). GitHub에서 받아 오기 같은 손 동작은 미리 설명하지 말고 그것이 필요한 날의 상자 하나로 준다. 루프 다섯 칸 이름은 ① 리서치하기 → ② 분석하기 → ③ 만들기 → ④ 내보내기 → ⑤ 반응 보기(11/21 "재기" → "반응 보기", 11/22 강사 문답 "모으기" → "리서치하기"(회사 말), "찾기" → "분석하기"). 11/24 스킬은 weekly-research, 부르는 한 줄은 "이번 주 리서치해줘".

- **사람 이름과 파일 이름, 화면 스크립트(11/22 13차).** 유저 스토리·예시 속 사람은 "사람 이름은 짓지 말고 팀장·동료·부사수로만"(가명이라고만 쓰면 모델이 실제 사람 같은 이름을 짓는다). 설계도에 적는 파일 이름은 그다음 날 상자가 실제로 만드는 이름 그대로 적게 하고, 아직 없는 파일은 (예정). 스크립트가 드는 화면을 만드는 상자에는 "스크립트는 함수 하나로 감싸고, top·name·status·parent처럼 브라우저가 이미 쓰는 이름은 변수로 쓰지 마"를 넣는다(전역 `var top`이 window.top과 부딪혀 빈 화면이 된 적이 있고, 모델의 가짜 화면 검사는 이것을 못 잡는다). 시험에서는 `check_outputs.js`로 진짜 브라우저에서 연다.

### 4. 프롬프트 쓰기
기준 문서 `classroom/standards/prompt-standard.md`를 먼저 읽는다. 핵심만:
- 끝까지 만든다 / 되묻지 않는다 / 빈칸이 없다(입력 칸으로 받고 비워 둬도 돈다) / 혼자 선다("○○가 없으면 먼저 만들고 이어서 해줘") / 짧다 / 보고는 3줄.
- 웹 조사 표: 줄마다 조사일과 출처 링크, 못 찾은 값은 "못 찾음", 원 단위 숫자, UTF-8 BOM, 쉼표·큰따옴표·줄바꿈이 든 값은 큰따옴표. 이 규칙은 P0이 CLAUDE.md에 심는다.
- Claude가 열지 못하는 자료(메타 광고 라이브러리 같은 것)가 핵심이면 학생이 직접 보고 붙여 넣는 단계를 기본으로 둔다(Day 16 P2-1).
- 칸이나 경쟁사를 바꾸는 한 줄에는 설계 파일도 같이 고치라고 붙인다("mvp.md의 칸도 같이 바꿔줘").
- **쉬운 말로 쓴다(11/16 강사 지시).** 축약된 한자어·업계어(과업, 테스터, 관찰 지표, 우선순위, 검증 기준 같은 것)는 `classroom/standards/easy-words.md`의 풀어 쓴 말로 쓰고, 처음 나오는 자리에만 "현업에서는 '○○'라고 불러요"를 붙인다. 프롬프트의 말도 같이 바꾼다. 그날 새로 나온 후보는 바꿀 말 보기와 예시 문장으로 강사에게 한 번 묻는다.
- 약자는 괄호로 영단어: 학생 자료는 문단마다 처음 한 번, 프롬프트는 줄마다 처음 한 번 "MVP(Minimum Viable Product)". 새 약자(MD, CX 같은 것)도 처음 나오는 곳에.
- 스킬은 한국어 한 줄로 부르게 한다. "/스킬이름"으로 부르면 한국어 규칙이 있어도 답이 영어로 나왔다.

### 5. 빌더로 페이지 만들기
`classroom/tools/build_day18.py`(공통 부분은 `guide_common.py`)를 `build_dayNN.py`로 복사해 프롬프트(PR)와 본문(body)만 바꾼다. 페이지 규칙과 빌더 쓰는 법은 `references/page-guide.md`. 요점: 아티팩트 이름 "Day N · 주제", 머리말 "Day N / 52 · 날짜", 맨 앞은 하루 지도(덩어리 세 개와 시간표), 구간 머리는 "덩어리 · 시간 · 교시 / 제목 / 왜 해요?", 입력 칸은 비워 두고 흐린 글씨로 처음 값.

### 6. 가상 학생으로 돌려 보기
`classroom/tools/runchain.py`로 가이드 HTML의 프롬프트를 뽑아 빈 폴더에서 학생처럼 이어서 보낸다. 갈래 짜는 법, 명령 예, 통과 기준, 이 환경에서만 생기는 일은 `references/testing.md`. 최소한: 보기마다 한 갈래 + 아무것도 안 바꾼 학생 + 보기에 없는 것을 직접 적은 학생 + 테크 트랙 + 회사를 바꾼 학생. 모든 상자를 한 번 이상 돌린다.

### 7. 화면 점검
`node classroom/tools/check_guide.js <가이드.html>`: 폰 폭 넘침, 복사 상자, 메뉴 링크, 입력 칸 → 파란 글자를 본다. 걸린 것이 있으면 고치고 다시. 시험에서 나온 학생 화면도 `node classroom/tools/check_outputs.js <화면.html>...`로 브라우저에서 열어 본다(빈 화면은 시험기가 못 잡는다). 이어서 `python3 classroom/tools/easy_words.py check <가이드.html>`로 옛말이 남았는지 본다(통과면 종료 코드 0).

### 8. 수강생 눈 검토
`node classroom/tools/guide_to_text.js <가이드.html> <글.txt>`로 글로 옮긴 뒤, 반의 유형에 맞춘 세 사람(그리고 Day 17부터는 강사 한 명이 반 전체와 수업을 굴리는 눈, 전날 가이드와 나란히 놓은 눈)(예: 비전공 콘텐츠 마케터 지망생, 현업 경력이 있는 학생, 테크 트랙)의 눈으로 서브에이전트에게 읽힌다. 지시문 틀은 `references/testing.md`. 돌아온 지적은 가이드 원문과 하나씩 대조하고 맞는 것만 고친다. 프롬프트를 고쳤으면 6단계로 돌아간다.

### 9. 발행
Artifact 도구로 발행한다. 이미 있는 날짜는 같은 링크(url)로 고쳐 올린다. 공유는 강사가 바꾼다("링크가 있는 사람"). 용어 사전(`build_glossary.py` → glossary.html)도 그날 말에 맞춰 고쳐 같은 링크로 올린다.

### 10. 강사 문서와 커밋
`references/instructor-docs.md`의 틀로 시연카드, 모의수업(예상 대화·검토 기록), 시험 결과, `HANDOFF.md`의 새 7-xx, 필요하면 `prompt-standard.md`를 고친다. 그다음 커밋·푸시한다(작업 브랜치, 공개 저장소라 개인정보가 없는지 한 번 더 본다).

## 강사에게 보고하는 틀

짧게, 해요체로. ① 무엇을 바꿨나(표 하나) ② 시험 결과(몇 회, 모두 끝까지 돌았는지, 걸린 것과 고친 것) ③ 강사가 정할 것 두세 개(질문으로) ④ 전날 확인할 것. 새 개념은 비유 한 줄, 업무 이야기는 입력 → 처리 → 출력 → 검증으로.

## 이미 만든 자료를 고칠 때의 표기 규칙 (11/16 강사 지시, Day 16 P5 "바뀐 곳" 구조를 따름)

| 규칙 | 하는 법 |
|---|---|
| 1. 고치기 전 판을 남긴다 | 발행본이면 고치기 전 버전 번호를 기록하고, 파일이면 `이름_v1`, 이미 있으면 다음 번호(`_v2`)로 남긴다. 덮어쓰지 않는다 |
| 2. 같은 것끼리 비교한다 | 같은 상자, 같은 구간, 같은 칸끼리 비교해 바뀐 곳 / 새로 생긴 곳 / 사라진 곳을 나눈다 |
| 3. 앞 값과 새 값을 같이 보인다 | "이전 → 지금"으로 적는다. 바뀐 값은 색이나 표시로 눈에 띄게 한다 |
| 4. (확인 필요)를 따로 둔다 | 근거가 흔들려 바뀐 것인지 모르는 곳(출처가 바뀜, 못 찾음 ↔ 값, 시험 못 함)은 "바뀐 곳"에 섞지 않고 따로 적는다 |
| 5. 바뀐 곳이 없으면 그렇게 쓴다 | "바뀐 곳 없음"과 비교한 날짜·시각을 적는다 |
| 6. 끝나면 표로만 보고한다 | 바뀐 곳 표와 (확인 필요) 표만 보인다. 둘 다 없으면 "바뀐 곳 없음"만 |

**어디에 적나:** 강사 보고(대화), HANDOFF의 해당 절 "바뀐 것" 줄(판 번호, 이전 → 지금), 강사 문서 맨 위 "이번 판에서 바뀐 것". 학생 화면에는 변경 기록을 넣지 않는다.
**고친 프롬프트:** 바뀐 상자 번호와 이전 문구 → 새 문구를 적고, 그 상자가 든 갈래를 처음부터 다시 시험한다. 발행본과 시험본이 글자 단위로 같은지도 확인한다.
